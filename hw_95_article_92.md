### 1 Интерактор с размытой границей ответственности

```kotlin
/**
 * Интерактор для управления кешом дерева устройств
 * Подумайте дважды, действительно ли нужно использовать этот интерактор или подойдет [TreeCacheRepository]
 */
interface TreeCacheInteractor {

    enum class ReloadMode { HARD, SOFT, NONE }

    suspend fun fetchAvailableHomes(reloadMode: ReloadMode = ReloadMode.NONE): Out<List<Union>>
    suspend fun selectCurrentHome(homeId: String?): UnionNode?
    suspend fun updateHome(homeId: String): UnionNode?
    suspend fun awaitFor(id: String?)
    suspend fun awaitForActiveHome(): UnionNode
    fun clear()
}
```

Как надо: разбить интерфейс по фактическим ролям клиентов, а не оставлять границу ответственности на усмотрение комментария. 
Например, вынести отдельно операции загрузки (`fetchAvailableHomes`, `selectCurrentHome`, `updateHome`) и отдельно - ожидание готовности кеша (`awaitFor`, `awaitForActiveHome`), 
каждой группе сформулировать явный и проверяемый контракт (что именно гарантирует `ReloadMode.NONE`, при каких условиях `awaitForActiveHome` не подвиснет). Т
Тогда выбор между этим интерактором и `TreeCacheRepository` перестанет быть вопросом "подумайте дважды" и будет закреплен самими типами.

### 2

```kotlin
interface MapCredentialsProvider {

    val apiKey: String

    val baseUrl: String
}
```

Реализация просто читает константу из `BuildConfig` и возвращает захардкоженную строку - никакой логики, а значит и вариативности, здесь нет вообще. 
Это не абстракция поведения, а два значения, обернутые в интерфейс; для подстановки других значений в тестах вообще не нужен мок - достаточно передать другой набор данных.

Как надо: убрать интерфейс совсем и заменить его неизменяемым значением:

```kotlin
data class MapCredentials(
    val apiKey: String,
    val baseUrl: String,
)
```

Значение один раз собирается в DI-модуле через `@Provides`, а для тестов вместо мока просто передаётся другой экземпляр `MapCredentials` с тестовыми данными - это проще и типобезопаснее любого мока.

### 3

```kotlin
internal interface RoomSensorsInteractor {

    suspend fun fetchSensorsFor(roomId: RoomId): RoomSensorsUiItem?

    suspend fun subscribeOnSensors(
        currentHomeId: String,
        roomId: RoomId,
        sensors: ImmutableList<SensorUiItem>,
    ): Flow<RoomSensorsUiItem>
}
```

Интерфейс и его единственная реализация объявлены прямо в одном файле - верный признак, что он появился не ради абстракции, 
а ради того, чтобы `ViewModel` можно было тестировать с моком. 
Второй реализации здесь никогда не предполагалось, а сам интерфейс даже не выходит за пределы модуля (`internal`).

Как надо: тестировать `RoomSensorsInteractorImpl` напрямую, с фейковыми `HomeFilterSelector` и `DeviceNodeToSensorUiMapper`, вместо мока целого интерактора в тесте `ViewModel` - конкретный класс тестируется ничуть не хуже интерфейса. 

### Выводы

Раньше я тоже заворачивал почти каждый Interactor/Repository/Provider в интерфейс - казалось, что так виднее публичный контракт класса и его проще подменить в тестах. 
После разбора этих примеров стало ясно, что реальной взаимозаменяемости почти нигде не было: у каждого интерфейса ровно одна реализация в проде, а единственный "второй implementer" - это мок в тесте. 
То есть настоящей причиной была не абстракция, а тестируемость, а ее вполне можно закрыть, тестируя конкретный класс напрямую или мокая его через `mockk` (он прекрасно мокает и открытые классы) - без лишнего интерфейса.

Заодно стало видно, что там, где абстракция все-таки настоящая - несколько реальных реализаций, между которыми осмысленно переключаться (как `DeviceCapabilities` с тремя реализациями, или гипотетический движок аналитики: Firebase, AppMetrica и свой собственный) - интерфейс работает ровно так, как задуман. 
Дело не в интерфейсах самих по себе, а в том, применяются ли они по назначению: как описание роли, которую могут играть разные объекты, а не как обертка вокруг единственного класса "для порядка".
