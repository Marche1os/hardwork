### 1.

Здесь nullable тип у roomName означает, что комнаты может не быть, если устройство не привязано к комнате.
При этом null, как и почти всегда, можно трактовать и как опциональность поля, и как ошибку, что свойство не пришло.
Лучше было бы использовать sealed class с типом комнаты и возможными состояниями: есть | нет 

```kotlin
data class Device(
    val id: String,
    val roomName: String?, // NULL, когда устройство не привязаоно к комнате
)
```

В БД такое можно моделировать через особый статус связности устройства с комнатой. Например, это будет enum, описывающий тип связи: HOME, если привязано только к дому и ROOM, если привязано к комнате

### 2

```kotlin
fun loadProfile(profileId: String): Profile? = null
```

Здесь null служит как ошибка загрузки. Но непонятно: может быть профиль не найден, может быть произошла ошибка парсинга структуры.
Лучше было бы иметь конкретный результат: пользователь не найден, ошибка парсинга и т.д.

### 3

```kotlin
class DeviceSettingsViewModel(
    getSettingsUseCase: GetDeviceSettingsUseCase,
    deviceId: String,
) {

    var settings: DeviceSettings? = null

    fun loadSettings() {
        getSettingsUseCase.execute(deviceId)
            .onSuccess { settings ->
                this.settings = settings
            }
    }

    fun onSettingClick(settingId: String) {
        //  Обращение к полю settings
    }
}
```

Null тут означает, что настройки еще не загрузились. Лучше было бы конкретные состояния использовать:

```kotlin
sealed interface UiState<out T> {
    data object NotInit : UiState<Nothing>
    data object Loading : UiState<Nothing>
    data class Success<T>(val data: T) : UiState<T>
    data object Empty : UiState<Nothing>
    data class Error(val throwable: Throwable) : UiState<Nothing>
}
```

### 4
Null для пустых коллекций. Часто для обозначения, что коллекция пуста, используется nullable List:

```kotlin
data class Event(
    val eventId: String,
    val tags: List<String>?,
)

// и далее tags?.forEach { tag -> 
// ...
// }
```

Здесь достаточно было бы использовать просто пустую коллекцию: emptyList. Или NonEmptyList из Arrow.

### 5

```kotlin
data class HeaderUiItem(
    val title: String,
    val subtitle: String?,
)
```

Здесь nullable тип опять же означает опциональность.
С String типом сложнее еще, что опциональность может быть выражена как nullable типом, так и пустой строкой. 
И получается нужно проверять оба кейса: и на null, и на пустоту.
Лучше использовать доменный тип, который не может быть создан, если строка пуста или тип null. И использовать обертку Optional<Subtitle>

### Выводы

На одном из проектов был сложный компонент - checkout, в котором было множество nullable параметров. 
При добавлении новых функций, в который требовалось прокидывать параметры, зачастую просто кидали null и не разбирались за что то или иное свойство отвечает и нужно ли оно для запросов.
Это часто ломало всю систему оплаты. И проблема тут в том, что NULL можно трактовать по-разному. В том случае большинство видело nullable тип и считали, что оно не нужно при заведении новых функций.

Частое использование NULL в проекте ознаачет отсутствие затрат на качественное проектирование компонент системы.
По возможности нужно заменять расплытое состояние, которое представляет собой null, на явное состояние. И тогда выразительность сильно повысится, а количество багов снизится.

Можно также упомянуть известную критику NULL, связанную с Тони Хоаром. 
Он называл введение null reference своей "ошибкой на миллиард долларов". 
Смысл этой формулировки в том, что специальное “пустое” значение оказалось источником огромного числа ошибок и сбоев. 
В контексте задания эта мысль хорошо подчеркивает главный вывод: NULL удобен локально, но при чрезмерном использовании делает систему менее надежной и менее выразительной.
