### 1 Интерфейс для мапинга

```kotlin
interface FilterUiMapper {
    
    fun map(filter: FilterDomain): FilterUiItem
}
```

По всему проекту принято выделять все в интерфейсы и в этом примере интерфейс для мапинга доменной сущности в UI модель.
Здесь интерфейс не является абстракцией, несколько реализаций маперов в принципе не может быть.

### 2

```kotlin
/**
 * UseCase на предзагрузку изображения по [url]
 */
interface PrefetchImageUseCase {

    suspend fun execute(url: String): Result<Unit>
}
```

Еще пример интерфейса, не являющегося абстракцией. 
По-сути это пример излишнего слоя абстракций. Типичная ситуация для Clean Architecture.

### 3

```kotlin
interface UserRepository {

    suspend fun loadUser(uid: String): Result<User>
}
```

Еще пример из типичной clean architecture: google рекомендует использовать интерфейс для репозиториев для создания Mocked репозитория, но на практике очень редко требуется иметь прям mock реализацию репозитория.
Для тестирования вполне успешно используется другой подход с mockk.
Поэтому это еще один пример плохой абстракции, где интерфейсу соответствует только одна реалихация.

### 4

```kotlin
interface FiltersAnalytics {
    
    fun logFilterShown(filter: Filter)
    
    fun logClick(filter: FIlter)
}
```

Здесь довольно очевидно, что никакой абстракции интерфейс не представляет. Другое дело был бы движок аналитики: firebase, appMetrica и др.

### 5

```kotlin
interface BannersCache {

    fun put(banner: List<Banners>): Boolean

    fun getCached(): List<Banner>
    
    fun clear()
}
```

С одной стороны может показаться, что такой кеш представляет собой хорошую асбтракцию. Как минимум может быть несколько реализаций: файловый кеш, in-memory.
Однако в проекте все такие кеши под собой инициализирует именно файловый кеш и используют конкретную библиотеку для кеширования.
Поэтому интерфейс становится избыточным.

### Выводы

Раньше я был большим поклонником использовать на все интерфейсы: это выделяло явно публичный функции и методы класса и давало понимание, как можно взаимодействовать с классом.
Однако интерфейсы не совсем использовались по назначению и в большинстве случаев их применение было избыточном и не отвечало их идее.
С выполнением данного занятия я пересмотрел свой взгляд на понятие абстракции в контексте интерфейса и нашел иные способы облегчить видение класса с помощью инструментов IDE. 
То есть одна из причин, по которой пихались всюду интерфейсы, порешилась.

Интерфейсы еще часто используются не по назначению из-за отсутствия в языке других способов выразить задумку. Например, есть интерфейсы-маркеры или интерфейсы-фичи. Которые добавляют классу некоторое поведение и возможности.
В Kotlin это хорошо работает в связке "интерфейс-делегат", что позволяет эмулировать множественное наследование.
И конечно такие интерфейсы не являются абстракциями и служат иной задумке.
