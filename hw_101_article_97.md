## Как я считал характеристики

Чтобы числа можно было сравнивать между собой, я сначала договорился с собой о единицах:

1. **Строки кода в проде.** Примерное число строк нашего кода, которые выполняются за один прогон теста. Код библиотек (OkHttp, Room, Compose) не считаю.
2. **Границы.** Сколько раз тест пересекает границу между нашими классами или модулями, которые в проде живут отдельно.
3. **Разбиение.** На сколько модульных тестов можно разложить проверку, если проверять каждую часть отдельно.
4. **Внешние сервисы.** Все, что не является нашим кодом и нужно для запуска: тестовый сервер, база, эмулятор, стенд.
5. **Усилия.** Оценка от 1 до 5 плюс то, что конкретно нужно для запуска.
6. **Нелокальность.** Сколько строк в худшем случае придется просмотреть, чтобы найти причину падения.
7. **Эмерджентность.** Моя оценка вероятности того, что падение вызвано не ошибкой в одной части, а их взаимодействием.

начну с обычного модульного теста.

### 0. Точка отсчета: маппер датчика дыма

```kotlin
@Test
fun `smoke flag is taken from new state`() {
    val state = converter.convert(type, attributeState(SMOKE_STATE to true), oldState = null)
    assertTrue(state.isSmoke)
}
```

| Характеристика | Значение |
|---|---|
| 1. Строки кода в проде | ~40 |
| 2. Границы | 0 |
| 3. Разбиение | 1 |
| 4. Внешние сервисы | 0 |
| 5. Усилия | 1, ничего, кроме JUnit |
| 6. Нелокальность | ~40 |
| 7. Эмерджентность | ~0% |

Все остальные тесты я сравнивал с этим.

### 1. Обновление токена при параллельных запросах

Два запроса одновременно получают 401.
Нужно проверить, что токен обновляется ровно один раз, и оба запроса повторяются уже с новым токеном.

```kotlin
@Test
fun `parallel 401 triggers single refresh`() = runTest {
    server.dispatcher = AuthDispatcher(expiredToken = "old", freshToken = "new")

    val results = List(2) { async { api.loadHomes() } }.awaitAll()

    assertTrue(results.all { it.isSuccess })
    assertEquals(1, server.requestsTo("/auth/refresh"))
    assertEquals("Bearer new", server.lastRequestTo("/homes").getHeader("Authorization"))
}
```

Работают настоящие `OkHttpClient`, наш `Interceptor`, `Authenticator`, провайдер токенов и хранилище, против `MockWebServer`.

| Характеристика | Значение |
|---|---|
| 1. Строки кода в проде | ~350 |
| 2. Границы | 5 (интерсептор, аутентификатор, провайдер токенов, API авторизации, хранилище) |
| 3. Разбиение | 4 |
| 4. Внешние сервисы | 1 (`MockWebServer`) |
| 5. Усилия | 3, свой `Dispatcher` для сервера и настоящий параллельный запуск корутин |
| 6. Нелокальность | ~400 |
| 7. Эмерджентность | ~40% |

Каждая часть по отдельности у нас покрыта, и эти тесты зеленые.
А вот гонка между двумя запросами существует только тогда, когда части работают вместе.
Модульный тест аутентификатора этого не поймает, у него нет второго запроса.

### 2. Удаление устройства из сокета до экрана

Пользователь держит открытым экран устройства, а в это время устройство удаляют с другого телефона.
Экран должен показать, что устройства больше нет, и не отправить в него ни одной команды.

```kotlin
@Test
fun `device screen reacts to removal from socket`() = runTest {
    socketServer.send(fixture("device_removed.json"))

    viewModel.state.test {
        assertEquals(DeviceScreenState.Removed, awaitItemMatching { it is DeviceScreenState.Removed })
    }
    assertEquals(0, httpServer.requestsTo("/commands"))
}
```

Цепочка такая: фейковый сокет-сервер, наш клиент сокета, разбор сообщений, кеш дерева, источник обновлений устройства, `ViewModel`.

| Характеристика | Значение |
|---|---|
| 1. Строки кода в проде | ~900 |
| 2. Границы | 7 |
| 3. Разбиение | 6 |
| 4. Внешние сервисы | 1 (`MockWebServer` с websocket upgrade) |
| 5. Усилия | 4, JSON фикстуры в отдельных файлах, тестовый модуль Hilt, Turbine, управление диспетчерами |
| 6. Нелокальность | ~1000 |
| 7. Эмерджентность | ~50% |

У нас был целый класс багов, когда клиент получал апдейт и шел в уже удаленное устройство.
Каждый раз ошибки были не в какой-то одной части, а в том, в каком порядке события проходили через кеш и подписку.
Поэтому этот тест я считаю одним из самых ценных.

### 3. Миграция базы Room

После обновления приложения кеш дома в базе должен пережить миграцию схемы с 7 на 8 версию без потери данных.

```kotlin
@Test
fun migrate7To8_keepsCachedHome() {
    helper.createDatabase(TEST_DB, 7).use { db ->
        db.execSQL("INSERT INTO homes (id, name) VALUES ('h1', 'Дача')")
    }

    val db = helper.runMigrationsAndValidate(TEST_DB, 8, true, MIGRATION_7_8)

    db.query("SELECT name, is_active FROM homes WHERE id = 'h1'").use { cursor ->
        assertTrue(cursor.moveToFirst())
        assertEquals("Дача", cursor.getString(0))
    }
}
```

| Характеристика | Значение |
|---|---|
| 1. Строки кода в проде | ~150 |
| 2. Границы | 2 (наша миграция и схема Room) |
| 3. Разбиение | 1, по частям SQL миграции честно не проверить |
| 4. Внешние сервисы | 1 (эмулятор или устройство с настоящим SQLite) |
| 5. Усилия | 4, экспортированные JSON схемы, `androidTest`, эмулятор в CI |
| 6. Нелокальность | ~150 |
| 7. Эмерджентность | ~15% |

Этот пример выбивается из остальных.
Нужен внешний сервис, писать и запускать тест дорого, но ошибка почти всегда локальна: она в одном SQL скрипте.
И на модульные тесты он не раскладывается, а не наоборот.
Тем не менее тест по ощущениям точно интеграционный: проверяется стык нашего кода с настоящим SQLite, который заменить моком нельзя.

### 4. Оптимистичное обновление команды и сокет

Пользователь включает лампу. UI сразу показывает "включено", команда уходит на бэкенд и падает с 500.
Пока ждем ответ, по сокету приходит старое состояние лампы.
В итоге UI должен откатиться к выключенной лампе и показать ошибку, а не застрять во включенном состоянии.

```kotlin
@Test
fun `optimistic state rolls back when command fails during socket update`() = runTest {
    httpServer.enqueue(MockResponse().setResponseCode(500).setBodyDelay(300, MILLISECONDS))

    viewModel.onAction(LampAction.Toggle)
    advanceTimeBy(100)
    socketServer.send(fixture("lamp_off_state.json"))
    advanceUntilIdle()

    val state = viewModel.state.value
    assertFalse(state.isOn)
    assertEquals(LampError.CommandFailed, state.error)
}
```

| Характеристика | Значение |
|---|---|
| 1. Строки кода в проде | ~700 |
| 2. Границы | 6 |
| 3. Разбиение | 5 |
| 4. Внешние сервисы | 2 (HTTP сервер и сокет сервер, оба фейковые) |
| 5. Усилия | 4, виртуальное время, задержки ответов, порядок событий из двух источников |
| 6. Нелокальность | ~800 |
| 7. Эмерджентность | ~70% |

Это самый эмерджентный тест из пяти.
По отдельности все верно: оптимистичное обновление применяется, ошибка команды откатывает изменение, сокет приносит актуальное состояние.
Но откат делался к состоянию на момент нажатия, и он затирал то, что успело прийти из сокета.
Ни один модульный тест этого не видел, потому что каждый из них знал только про один источник событий.

### 5. Сценарий на стенде

Полный путь через UI: войти тестовым аккаунтом, выбрать дом, включить виртуальную лампу и проверить через API стенда, что лампа действительно включилась.

```kotlin
@Test
fun toggleVirtualLamp_onStaging() {
    loginAs(TestAccounts.smokeUser)
    composeRule.onNodeWithText("Тестовый дом").performClick()
    composeRule.onNodeWithTag("device_virtual_lamp_toggle").performClick()

    eventually(timeout = 10.seconds) {
        assertTrue(stagingApi.deviceState("virtual_lamp").isOn)
    }
}
```

| Характеристика | Значение |
|---|---|
| 1. Строки кода в проде | ~6000 на клиенте, плюс код бэкенда |
| 2. Границы | 15+ |
| 3. Разбиение | 20+ |
| 4. Внешние сервисы | 4 (бэкенд стенда, сервер авторизации, шлюз сокетов, эмулятор) |
| 5. Усилия | 5, тестовый аккаунт, секреты в CI, эмулятор, скрипт сброса данных на стенде |
| 6. Нелокальность | весь клиент и часть бэкенда, точно больше 10000 |
| 7. Эмерджентность | ~80% |

Сюда же добавляется нестабильность: тест иногда падает из-за стенда, а не из-за кода.
Строго говоря, это уже скорее E2E, и в выводах я пишу, почему все-таки его сюда взял.

## Выводы

Когда я свел все в одну таблицу, идея семейного сходства стала очень наглядной.
У тестов 1, 2 и 4 высокие значения почти по всем характеристикам сразу, и никаких сомнений в том, что они интеграционные, нет.
А миграция Room по половине характеристик ближе к модульному тесту, чем к интеграционному.
Строк мало, ошибка локальна, эмерджентности почти нет.
Интеграционным его делают только внешний сервис и усилия на запуск.
То есть общего признака, который был бы у всех пяти тестов, действительно нет.

Характеристики заметно связаны между собой.
Число границ, разбиение и нелокальность почти всегда растут вместе: если тест пересекает 6 границ, то и разложить его можно примерно на 5-6 частей, и искать причину падения придется по всей цепочке.
Независимо от них ведут себя две характеристики: внешние сервисы и эмерджентность.
Миграция показывает, что можно зависеть от внешнего сервиса без всякой эмерджентности.
А тест 4 показывает, что эмерджентность бывает и с фейковыми серверами.

Самой важной характеристикой для меня оказалась под номером 7.
Ради нее интеграционные тесты и стоит держать.
Тесты 1 и 4 существуют потому, что модульные тесты были зеленые, а ошибка все равно была.
Если у интеграционного теста низкая эмерджентность, стоит спросить себя, не заменить ли его несколькими модульными, которые быстрее и точнее показывают причину.

Это отвечает и на вопрос, может ли модульный тест поймать эмерджентность.
Найти ее модульный тест не может, он видит только одну часть.
Но после того как ошибку нашли, ее можно перевести в контракт одной из сторон.
В тесте 4 я бы добавил версию в состояние лампы и правило, что откат не может затереть более новую версию.
Это правило проверяется уже обычным модульным тестом редьюсера, за миллисекунды и с точным указанием причины.
Интеграционный тест находит эмерджентность, модульный тест на контракт закрепляет результат.
Так совет про контракты и assert-ы уменьшает нелокальность на практике.

Про E2E. Сценарий на стенде формально просто стоит выше всех по каждой характеристике, но мне кажется, что отличие у него качественное, а не только количественное.
Во-первых, он проверяет систему со стороны пользователя и ничего не знает о том, как она устроена внутри.
Во-вторых, его падение говорит только о том, что "что-то сломалось", и половина таких падений вообще не про код, а про стенд.
Тесты 1-4 знают, какие именно части они соединяют, и по упавшему тесту уже понятно, в какой цепочке искать.
Поэтому я бы провел границу так: интеграционный тест проверяет конкретный стык, E2E проверяет, что пользователь может сделать конкретную вещь.

Еще заметил, что моки и фейковые сервера действительно снижают часть значений, но не бесплатно.
`MockWebServer` убирает настоящий бэкенд из теста 1, но взамен появляется `Dispatcher` на 60 строк, который тоже может быть неправ.
Характеристика 4 уменьшилась, а характеристика 5 выросла.
Получается, усилия на тестовую инфраструктуру это тоже код, и его тоже нужно учитывать в стоимости теста.

Для себя я делаю такой практический вывод.
Не важно, как называть тест, модульным или интеграционным.
Важно смотреть на две вещи: какую эмерджентность он может поймать и сколько стоит его поддержка.
Если первое близко к нулю, а второе высокое, тест лучше переделать или заменить.
