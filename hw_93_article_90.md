## Генерико-подобные абстракции

### Выражают абстрактные свойства

- **ФП:** Haskell `Monoid`, абстрактное свойство "ассоциативная операция плюс нейтральный элемент", без привязки к предметной области.
- **ООП :** `fun <T : Comparable<T>> max(a: T, b: T): T = if (a >= b) a else b`. Ограничение `Comparable<T>` выражает абстрактное свойство упорядочиваемости, а не понятие какого-то домена.

### Спецификации бессрочны

- **ФП:** Законы `Functor` (`fmap id = id`, `fmap (f . g) = fmap f . fmap g`) зафиксированы математически и не меняются.
- **ООП:** Контракт `Comparable.compareTo` (антисимметричность, транзитивность) не менялся с момента появления интерфейса.

### Идентификация идиом (не буквальный смысл)

- **ФП:** `Foldable` идентифицирует идиому свертки, применимую к списку, дереву, `Maybe`, а не буквальное понятие "сворачиваемая вещь".
- **ООП :** `Iterable<T>` идентифицирует идиому обхода `for (x in collection)`, а не домен-термин "нечто перечислимое".

### Статическая типизация

- **ФП:** Ограничение `Ord a => a -> a -> Bool` проверяется компилятором Haskell.
- **ООП:** Ограничение `<T : Comparable<T>>` проверяется компилятором Kotlin на этапе компиляции.

### Полиморфизм времени компиляции

- **ФП:** Диспетчеризация словаря тайпклассов: `sort :: Ord a => [a] -> [a]` специализируется под каждый тип при компиляции.
- **ООП:** `inline fun <reified T> typeName(): String = T::class.simpleName!!`. Благодаря `inline`/`reified` компилятор генерирует специализированный код под каждый конкретный `T`.

### Механизм генерализации

- **ФП:** `map :: (a -> b) -> [a] -> [b]`, параметрический полиморфизм по элементу.
- **ООП:** `class Box<T>(val value: T)`, обобщение контейнера по типу `T`.

## Интерфейсо-подобные абстракции

### Выражают понятия предметной области

- **ФП:** F# `interface IPaymentGateway`, понятие обработки платежа.
- **ООП:** `interface PaymentGateway { fun charge(amount: Money): PaymentResult }`, то же понятие обработки платежа.

### Реализации имеют срок действия

- **ФП:** Запись функций `ShippingCalculator2024`, которую заменяет `ShippingCalculator2025` при изменении тарифов.
- **ООП:** `class TaxCalculator2024 : TaxCalculator`, которую в следующем году заменит `class TaxCalculator2025 : TaxCalculator` из-за изменений в налоговом законодательстве.

### Конструирование паттернов

- **ФП:** Final tagless / typeclass-based интерпретатор в Haskell как реализация паттерна Interpreter.
- **ООП:** `fun interface ShippingStrategy { fun calculate(order: Order): Money }` с несколькими реализациями, подставляемыми в `PaymentService`. Классический паттерн Strategy.

### Динамическая реализация (рантайм)

- **ФП:** Экзистенциальный тип `data AnyShape = forall a. Shape a => AnyShape a`. Конкретная реализация выбирается в рантайме по конфигу.
- **ООП :** `val service = PaymentService(gateway = resolveGatewayFromConfig())`. Конкретная реализация `PaymentGateway` подставляется в рантайме, например через DI-контейнер.

### Динамический полиморфизм

- **ФП:** F# `IShape.Area()`, виртуальный вызов через vtable .NET, тип объекта известен только в рантайме.
- **ООП:** `val s: Shape = Circle(radius = 24); s.area()`. Вызов резолвится через флаги байт-кода в рантайме в зависимости от фактического типа объекта.

### Механизм инкапсуляции

- **ФП:** OCaml module signature (`.mli`), тип `t` абстрактный, наружу выставлены только функции.
- **ООП :** `class StripeGateway(private val apiKey: String) : PaymentGateway { override fun charge(amount: Money): PaymentResult { TODO("not yet implemented) } }`. `apiKey` скрыт модификатором `private` и доступен только через методы интерфейса.

## Выводы

Генерико-подобные и интерфейсо-подобные абстракции это два независимых измерения абстракции, а не два способа делать одно и то же. 
Первые выражают вневременные, абстрактные, математические свойства. 
Вторые изменчивые понятия предметной области.

ФП действительно сильнее в генерико-подобных абстракциях: система типов Haskell/ML заточена под параметрический полиморфизм, законы тайпклассов и статическую проверку. 
Отсюда естественное превосходство ФП в алгоритмических задачах.

Интерфейсо-подобные абстракции в ФП не отсутствуют, а недооценены из-за предубеждения против ООП-стиля мышления. 
F# и OCaml показывают, что модули, сигнатуры и интерфейсы прекрасно выражают доменные понятия функциональным способом, просто это требует более осознанного проектирования, чем в ООП, где абстракция часто возникает сама собой из наследования и полей.


При проектировании модуля стоит сначала определить, к какому виду абстракции тяготеет задача. 
Если нужна обработка данных, инварианты, трансформации без внешнего состояния, стоит тянуться к параметрическому полиморфизму, тайпклассам и дженерикам, статическим проверкам. 
Это генерико-подобная абстракция, и здесь оправдан ФП-стиль даже в ООП-языке (хоть Kotlin и мультипарадигменный)

Если нужна замена реализаций во времени, конфигурация под окружение, интеграция с внешними системами (платежные шлюзы, хранилища, нотификации), стоит явно проектировать интерфейс с осознанием, что реализация имеет срок годности, и закладывать точку подмены (DI, стратегия, фабрика) заранее, а не как задел на будущее без конкретной цели.
Например, сейчас в рабочем проекте делаются SIP звонки, по-сути вся фича это работа с внешним миром. Сейчас используется один SIP-клиент, затем может быть другой. И здесь обязательно нужно учесть возможность легко изменить реализацию без изменения интерфейса.
