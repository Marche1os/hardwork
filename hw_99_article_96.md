## Интерфейсы по ISP, но не поверхностные

Для себя я развел эти два понятия так.
ISP отвечает на вопрос, сколько ролей в интерфейсе. Роль должна быть одна, и клиент не должен зависеть от того, что ему не нужно.
Shallow Interface про другое: сколько работы интерфейс снимает с клиента. Поверхностный интерфейс маленький, но клиенту приходится самому собирать из его методов нужное поведение: помнить порядок вызовов, проверять состояние, обрабатывать крайние случаи.
Нужен интерфейс, который одновременно маленький и глубокий: методов один-два, а за ними спрятано много логики.

### 1. TokenProvider вместо AuthStorage

Ранее я делил `AuthStorage` на `ReadOnlyAuthStorage`, `ReadWriteAuthStorage` и отдельный интерфейс очистки.
Формально с ISP после этого все в порядке, но интерфейсы получились поверхностными: это просто нарезанный CRUD над хранилищем.

```kotlin
interface ReadOnlyAuthStorage {
    fun readAuthToken(): String
    fun readRefreshToken(): String
}
```

Вся работа остается на клиенте. Сетевой слой должен сам прочитать токен, проверить, не истек ли он, при необходимости прочитать refresh токен, сходить за новым, записать оба обратно, а если обновить не получилось, очистить хранилище.
Плюс гонка: два параллельных запроса одновременно видят протухший токен и оба идут его обновлять.

Глубокий вариант для той же роли:

```kotlin
interface TokenProvider {

    /** Возвращает токен, с которым можно идти в сеть прямо сейчас */
    suspend fun validToken(): AuthToken

    /** Сервер отклонил [rejected]. Вернет новый токен или null, если сессия закончилась */
    suspend fun refreshAfterReject(rejected: AuthToken): AuthToken?
}
```

Что спрятано за двумя методами:

* чтение из хранилища и проверка срока жизни с запасом на рассинхрон часов;
* поход за новым токеном и запись результата;
* `Mutex`, чтобы при параллельных запросах обновление шло один раз, а остальные получили уже готовый токен;
* сравнение `rejected` с текущим токеном: если его уже обновил соседний запрос, второй раз обновлять не нужно;
* завершение сессии, если refresh токен тоже отклонен.

С точки зрения ISP интерфейсом пользуется только сетевой слой (`Interceptor` и `Authenticator` OkHttp), и оба метода нужны именно ему.
Экрану логина нужен свой `SessionStarter` с `login(credentials)`, а экрану настроек свой `SessionTerminator` с `logout()`. Ролей три, интерфейсов тоже три, и ни один из них не превращается в толстый `AuthManager`.

### 2. ActiveHomeSource вместо части TreeCacheInteractor

Возьмем `TreeCacheInteractor` с шестью методами. Раньше я предлагал разделить его на загрузку и ожидание. 
Сейчас вижу, что даже после такого разделения интерфейсы остались бы поверхностными:

```kotlin
interface HomeLoading {
    suspend fun fetchAvailableHomes(reloadMode: ReloadMode = ReloadMode.NONE): Out<List<Union>>
    suspend fun selectCurrentHome(homeId: String?): UnionNode?
}

interface HomeAwaiting {
    suspend fun awaitForActiveHome(): UnionNode
}
```

Клиенту по-прежнему нужно знать, какой `ReloadMode` выбрать, что сначала нужно дождаться готовности кеша и только потом читать, а для обновлений подписываться где-то еще.
Хотя большинству экранов нужно одно: текущий дом и его изменения.

```kotlin
interface ActiveHomeSource {
    val activeHome: Flow<UnionNode>
}
```

За одним свойством оказывается почти весь бывший интерактор:

* сначала дом из кеша, потом актуальный с бэкенда;
* ожидание готовности дерева. `awaitForActiveHome()` превращается в `activeHome.first()`, и отдельный метод больше не нужен;
* при смене дома приходит новое значение;
* обновления дерева по сокету;
* `distinctUntilChanged`, чтобы экраны не перерисовывались на одинаковых данных;
* повтор загрузки при ошибке.

`ReloadMode` пропал из клиентского кода совсем. Решать, когда перезагружать дом, должна реализация, а не каждый экран. Именно это и есть глубина: решение, которое раньше размазывалось по клиентам, теперь принимается в одном месте.

Выбор дома это отдельная роль, и нужна она только экрану выбора дома:

```kotlin
interface HomeSelector {
    suspend fun select(homeId: String)
}
```

### 3. DeviceUpdates вместо подписки с флагом


```kotlin
interface DeviceSocket {
    fun connect()
    fun subscribe(deviceId: String)
    fun unsubscribe(deviceId: String)
    fun addListener(listener: (String) -> Unit)
    fun removeListener(listener: (String) -> Unit)
}
```

Методы маленькие, но клиенту нужно вызывать их в правильном порядке, не забыть отписаться, самому разбирать сырые сообщения и самому понимать, что устройство удалено.

Глубокий вариант:

```kotlin
interface DeviceUpdates {
    fun observe(deviceId: String): Flow<DeviceUpdate>
}

sealed interface DeviceUpdate {
    data class Changed(val state: AttributeState) : DeviceUpdate
    data object Removed : DeviceUpdate
}
```

Что внутри:

* подключение к сокету и переподключение;
* подсчет подписчиков: два экрана на одно устройство дают одну подписку на сервере, а отписка происходит, когда уходит последний подписчик;
* повторная подписка после переподключения;
* разбор сообщений и отсев дублей.

Отписка теперь это просто отмена корутины, отдельный метод не нужен.
Флаг `withDeleteEvent` тоже исчез: удаление стало частью типа, и `when` по `DeviceUpdate` не даст про него забыть.
Тот самый класс багов, ради которого добавляли флаг (клиент получил апдейт и пошел в уже удаленное устройство), теперь закрыт на уровне компилятора.

Заодно этот интерфейс проходит проверку на композит из прошлого задания. `Flow` устроен как последовательность: Null Object это `emptyFlow()`, а композит это `merge` нескольких потоков.

## Closure of Operations

### 1. AttributeState и слияние состояний

У `AttributeState` уже есть `replace`, и я его постоянно использовал, не задумываясь, что это замыкание операций:

```kotlin
class AttributeState(
    private val values: Map<AttrKey, AttributeValue> = emptyMap(),
) {
    fun replace(other: AttributeState): AttributeState =
        AttributeState(values + other.values)

    companion object {
        val EMPTY = AttributeState()
    }
}
```

`AttributeState` на входе, `AttributeState` на выходе. Пустое состояние нейтрально: `a.replace(EMPTY) == a`.
Операция ассоциативна: `a.replace(b).replace(c)` равно `a.replace(b.replace(c))`, потому что при сложении мап побеждает правая сторона. Я проверил это и в коде.

Что это дает на практике:

```kotlin
// пачка апдейтов из сокета применяется одной сверткой
val actual = patches.fold(current, AttributeState::replace)

// оптимистичное обновление: команда поверх состояния с сервера
val shown = serverState.replace(pendingCommand)
```

Благодаря ассоциативности апдейты, которые часто приходят пачками, можно сначала склеить между собой, а потом один раз применить к состоянию устройства. Результат будет тем же, что и при применении по одному. Без замыкания и ассоциативности это пришлось бы отдельно доказывать и тестировать.

Важно, чтобы `replace` таким и оставался. Если он начнет зависеть, например, от `DeviceType` или что-то проверять снаружи, замыкание сломается, и все эти свертки перестанут быть безопасными.

### 2. Настройки света и сценарии

В hw_62 я делал `fun interface LightControl { fun apply() }`. 
Это команда, и сценарии из таких команд не складываются: "вечер" и "ночной режим" так и остаются отдельными реализациями.
Если замкнуть операции на настройках света, то сценарии начинают собираться из готовых кусков.

```kotlin
class LightSettings private constructor(
    val brightness: Int,
    val temperature: Int,
) {
    fun with(
        brightness: Int = this.brightness,
        temperature: Int = this.temperature,
    ) = of(brightness, temperature)

    companion object {
        fun of(brightness: Int, temperature: Int) = LightSettings(
            brightness = brightness.coerceIn(0, 100),
            temperature = temperature.coerceIn(2700, 6500),
        )
    }
}

fun interface LightAdjustment {

    fun adjust(settings: LightSettings): LightSettings

    infix fun then(next: LightAdjustment) = LightAdjustment { next.adjust(adjust(it)) }

    companion object {
        val NONE = LightAdjustment { it }
    }
}
```

Здесь сразу два замыкания. `adjust` переводит `LightSettings` в `LightSettings`, а `then` из двух корректировок делает корректировку. `NONE` нейтрален для `then`.

```kotlin
fun dim(percent: Int) = LightAdjustment { it.with(brightness = it.brightness * (100 - percent) / 100) }
fun warm(kelvin: Int) = LightAdjustment { it.with(temperature = it.temperature - kelvin) }
fun limitBrightness(max: Int) = LightAdjustment { it.with(brightness = minOf(it.brightness, max)) }

val evening = warm(1500) then dim(40)
val nightMode = evening then limitBrightness(10)

// сценарий из настроек пользователя
val custom = userAdjustments.fold(LightAdjustment.NONE, LightAdjustment::then)
```

Новый сценарий это новая комбинация, а не новый класс или метод в `LightController`.
Все инварианты живут внутри `LightSettings`: яркость от 0 до 100, температура от 2700 до 6500. Поэтому любая цепочка корректировок дает корректный результат. Я специально проверил на `warm(5000) then dim(200)`: получилась яркость 0 и температура 2700, а не отрицательные числа.
Это ровно то, что в статье описано для агрегатов DDD: если целостность обеспечивает сам тип, операции над ним можно комбинировать как угодно.

Одна оговорка: операция ассоциативна, но не коммутативна. `dim(50) then limitBrightness(10)` и `limitBrightness(10) then dim(50)` дают разную яркость. 
Для сценариев это нормально, порядок шагов тут часть смысла.

## Выводы

Главное, что я понял: ISP и глубина интерфейса друг от друга не зависят.
В одном из прошлых заданий hardwork я честно выполнил ISP и получил три маленьких интерфейса, но поверхностных: `AuthStorage` просто разрезали по операциям хранилища, а вся работа осталась на клиенте.
ISP считает роли, глубина показывает, сколько работы интерфейс забирает у клиента. Проверять нужно и то, и другое.

Все три поверхностных варианта повторяют устройство реализации: прочитать и записать, подключиться и подписаться, загрузить и подождать.
Глубокие варианты повторяют вопрос клиента: дай валидный токен, какой сейчас дом, что происходит с устройством.
Похоже, это и есть рабочий способ получить глубокий интерфейс: проектировать от того, что клиенту нужно, а не от того, что реализация умеет.

Признаки поверхностного интерфейса, которые я для себя выделил:

* клиент должен вызывать методы в определенном порядке;
* в параметрах есть флаги и режимы (`ReloadMode`, `withDeleteEvent`), то есть клиент принимает решения, которые должна принимать реализация;
* одинаковый код оркестрации повторяется в нескольких клиентах;
* есть отдельные методы на жизненный цикл (`connect`, `unsubscribe`, `removeListener`).

Отдельно отмечу `Flow`. В двух примерах из трех он позволил спрятать подписку, обновления и отписку за одним свойством или методом. Для Android это, наверное, самый простой путь от поверхностного интерфейса к глубокому.

По Closure of Operations главный эффект тот, что новое поведение появляется за счет комбинации существующих значений, а не новых методов. Работает это при трех условиях:

* инварианты живут внутри типа. Если бы `LightSettings` не ограничивал значения, каждую корректировку пришлось бы проверять отдельно, и комбинировать их свободно было бы нельзя;
* операция ассоциативна. Это дает право группировать и склеивать, как с пачками апдейтов;
* есть нейтральный элемент. Он бесплатно закрывает пустой случай в `fold`.

Интерфейсы с замыканием операций автоматически проходят проверку на композит: `then` и есть композит, а `NONE` и есть Null Object.
То есть Closure of Operations это не отдельный трюк, а лучший случай той же идеи. 
Если тип удается замкнуть, хорошая абстракция получается почти сама.
Получается это, правда, не всегда. `TokenProvider` и `DeviceUpdates` не замкнуты и возвращают другие типы. 
Но `DeviceUpdates` хотя бы возвращает последовательность, а это следующая по качеству категория.
