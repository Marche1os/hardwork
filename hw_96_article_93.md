### 1 пример плохого использования дефолтных параметров

```kotlin
/**
 * Загрузить дом из кеша. [forceReload] - требуется ли форсировать загрузку дома с бекенда
 */
fun loadHomeCache(forceReload: Boolean = false) {
    // загружаем дом
}
```

Здесь дефолтный параметр скрывает из вызывающего кода важную опцию - требуется ли актуализация данных.
О таком параметре легко забыть, о нем можно не знать при чтении кода и в целом это создает дополнительную когнитивную нагрузку при чтении из-за скрытой опции;

### 2 пример плохого использования

```kotlin
/**
 * Подписаться на устройство
 * [withDeleteEvent] - получать ли события удаления устройства
 */
fun subscribeOnDevice(deviceId: String, withDeleteEvent: Boolean = false) {
    // подписка на устройство 
}
```

Здесь параметр withDeleteEvent был добавлен как костыль, так как довольно часто случались баги: клиент получал апдейт по устройству и что-то с ним делал. 
А если этот апдейт - удаление, то шло обращение к удаленному устройству, что вело к разного рода багам.
Но вообще и здесь этот параметр - зло, так как значительно влияет на поведение. 

### 1 пример хорошего использования

```kotlin
fun createOkHttpClient(
    connectionTimeoutMs: Long = 10_000,
    useSecureClient: Boolean = true,
    retryCount: Int = 3,
) {
    // создание ok http клиента
}
```

Здесь я бы сказал, что это хороший пример использования параметров, поскольку они конфигурационные и содержит частоиспользуемые значения.

### 2 пример хорошего использования
```kotlin
@Composable
fun PrimaryButton(
    label: String,
    textColor: Color = Color.Black,
    buttonColor: Color = Color.White
) {
    // UI элемент - кнопка
}
```

Здесь используются дефолтные параметры для стиля кнопки. Цвета из дизайн-системы, поэтому чаще всего именно такие.
И если в ДС что-то поменяется, то легче будет мигрировать все кнопки на новый стиль. 
Это хороший пример, так как дефолтные параметры в данном случае избавляют от необходимости каждый раз задавать один и тот же стиль, что и снижает риск ошибки.

### Выводы

Дефолтные параметры действительно упрощают код в ситуациях, когда:
- параметры второстепенны и в большинстве вызовов достаточно стандартного значения
- дефолты заменяют громоздкие цепочки перегрузок
- в связке с именованными аргументами повышается читаемость вызова функции

Однако бывают и ситуации, когда дефолты создают больше проблем:
- когда значение по умолчанию вычисляется в момент вызова функции. Так снижается предсказуемость поведения
- когда дефолт значительно меняет логику поведения.

Плюс стоит отметить, что использование дефолтов в api библиотек также может создать проблемы из-за того, что значение встраивается в байт-код этапе компиляции.

В целом можно выделить, что дефолты мы используем в двух случаях: в целях конфигурации (например, UI элемент) и в целях изменения логики поведения.
Первый кейс чаще хороший и действительно упрощает код, во втором случае наоборот создает скрытые риски и чаще является примером плохого проектирования.
Так что можно заключить, что, как и почти всегда, дефолты это не универсально "плохой" или "хороший" механизм.
Важно то, как мы это используем.
